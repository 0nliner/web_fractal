# Извлечение модуля

Превращение модуля монолита в отдельный сервис — работа механическая и каждый
раз одинаковая: найти, от чего модуль зависит, найти, кто зависит от него,
сгенерировать проект и заменить внутрипроцессные вызовы клиентом.

```bash
wf extract orders            # сухой прогон: печатает план, ничего не меняет
wf extract orders -p grpc --no-dry-run
```

## План

`FractalExtractor` обходит граф зависимостей модуля в archtool и строит
`ExtractPlan`, где описано:

* проект отдельного сервиса, который будет сгенерирован;
* `inner_integrations/<module>/` в монолите — HTTP-, gRPC- или Kafka-клиент с
  тем же интерфейсом, что был у модуля, чтобы вызывающие продолжали звать тот
  же ABC;
* зависимости, которые поедут вместе с модулем, и те, которые пришлось бы
  разорвать.

```python
from web_fractal.core.extraction import FractalExtractor

plan = FractalExtractor(...).build_plan("orders")
```

Сухой прогон стоит по умолчанию не из осторожности: полезная часть — это как
раз план. Большинство модулей с первого захода не извлекаются, и список
зависимостей, которые пришлось бы разорвать, и есть настоящий ответ: он
показывает, что чинить до того, как что-то поедет.

## Почему интерфейс переживает переезд

Вызывающие зависят от ABC модуля, а не от реализации. Сгенерированный клиент
реализует тот же ABC поверх сети, поэтому места вызовов не меняются — меняется
только то, что зарегистрировано в инжекторе. Ради этого интерфейсы и объявляют
отдельно, и на извлечении это окупается.
